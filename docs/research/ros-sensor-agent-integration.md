# 机器人端多模态感知、ROS 兼容与 Agent 协作

日期：2026-09-08。用户目标：机器人端 Agent 负责声音、触觉／力觉、视觉、SLAM 等本机能力，并与工作站／云端 Agent 对话协作；不是让工作站逐个遥控机器人工具。本轮为方案与现状核对，未安装或启动 ROS、传感器或 SLAM。

## 结论

Loop ROS 可以作为 ROS 1／ROS 2 上层的机器人 Agent 运行与协作层，复用现成驱动、感知、建图和控制软件；目前不能宣称已经完整兼容或替代 ROS。SLAM 等模块应作为可独立运行的常驻程序，由 Loop 工具链适配和管理。直接执行解决程序怎么运行，工具链解决 Agent 怎样可靠使用它，两者不是二选一。

机器人端 Agent 管理自己的能力、运行状态、已验证操作与任务取舍；工作站 Agent 协商目标、处理复杂开发和全局分析。高频采样与控制交给确定性驱动和算法循环；大模型按问题／事件调用，不负责逐帧采样或实时伺服。

## 建议结构（待实现）

```text
工作站／云端 Agent ⇄ 目标、约束、进度、追问、证据 ⇄ 机器人端 Loop Agent
                                                    │
                                         本地能力工具链与状态摘要
                                                    │
                       ROS 1 adapter / ROS 2 adapter / 原厂 SDK adapter
                                                    │
                       声音、相机、触觉／力觉、IMU／激光、SLAM／控制
```

为各能力区分三类内容：常驻数据流、Agent 可调用的操作、可验证的健康状态。复用现有 PermissionGate、App.resources、设备所有权与 Task/Node 生命周期，不另建跨工具预算账本。SLAM 包优先留在其正常 ROS 工作区及环境中，通过独立适配进程接入；不把全部 ROS 依赖强塞进标准库 core 或 Loop Python 环境。

| 能力 | 持续运行的底层工作 | Agent 需要的接口与结果 |
| --- | --- | --- |
| 声音 | 采样、缓存；按需 VAD／识别／定位 | 当前声源／语音事件、指定时间片段、采样健康状态 |
| 触觉／力觉 | 采样、标定变换、滤波与本地控制响应 | 接触位置、标定后力／力矩、趋势和事件；注明测量或估计，不能把电流直接当实际接触力 |
| 视觉 | 相机采集、时间同步、按需检测／跟踪 | 指定时刻图像、目标与位姿、标定与坐标系信息 |
| IMU／激光 | 采样、预处理、局部缓存 | 姿态／距离／点云摘要以及按需原始片段 |
| SLAM | 持续里程计／定位／建图与回环优化 | 启动／暂停或停止（按包实际能力）、当前位姿与有效性、地图保存和定位故障 |
| 控制 | 驱动或控制器执行确定性闭环 | 下发有限目标、进度／结果／取消与本地停止反馈 |

统一观测应带来源、传感器标识、源时间和接收时间、时钟域、frame_id、单位、标定／地图版本、状态有效性和数据引用。ROS 1 时间、ROS 2 时间、仿真 /clock 不能未经转换混用；TF 与 QoS／队列策略需按实际传感器验证。音频／触觉没有覆盖所有硬件的单一标准消息，应保留厂商接口并在适配层转换。

原始高带宽数据优先留在端侧环形缓存或记录文件中，Agent 日常使用摘要和事件；远端明确需要时，再传图像、音频、点云、轨迹片段或对应文件。若本机资源不足，可协商把特定感知计算放到工作站，同时明确带宽、时延与断线行为，不等同于永久把所有数据送入云端模型。低延迟接触处理和控制不能依赖两端大模型对话往返。

## SLAM 如何接入

传感器数据和坐标变换 → 已有 SLAM 节点 → 地图、位姿和状态 → 端侧 Agent 工具。初次调试可直接用包自己的启动命令，确认实际输入、TF、参数和输出；稳定后保存为机器人能力配置，Agent 使用已有配置启停／查询，不临时拼接陌生指令。

候选例子，不代表已安装或选定：

- [SLAM Toolbox](https://github.com/SteveMacenski/slam_toolbox)：可用于 2D 激光建图和定位，按实际 ROS 分支选择。
- [RTAB-Map ROS](https://github.com/introlab/rtabmap_ros)：有 ROS 集成及 RGB-D、双目、3D 激光示例，按输入和 ROS 分支验证。

SLAM 提供地图和定位；目标导航／路径规划／控制是后续能力，不能把“地图节点启动”当成自主导航完成。验收至少对应当前任务需要的实际输入、有效输出和目标产物；不额外强加与任务无关的检查。

## ROS 1 与 ROS 2 兼容策略

优先设计两种原生适配器，向 Loop 暴露同一能力接口：ROS 1 适配其 topics/services/actionlib、参数和启动方式；ROS 2 适配 topics/services/actions、参数、QoS、TF 和适用的 lifecycle 节点。两端软件可留在独立进程／环境中，避免 ROS 的系统 Python／二进制依赖与 Loop Python 相冲突。ROS 2 lifecycle 并非每个节点都实现，启动命令也不能自动视为就绪。

既有 ROS 1 与 ROS 2 数据需要互通时，可选择 [ros1_bridge](https://github.com/ros2/ros1_bridge)。官方说明它主要桥接编译时已支持的消息和服务；自定义接口通常需在两端构建后重新构建桥，不能假定 actions、所有参数或全套应用自动透明兼容。官方仓库还指出 Noetic 已于 2025 年 5 月结束维护，Ubuntu 24.04 不支持其正常 ROS 1／bridge 组合。因此新项目优先 ROS 2，旧机器人保留 ROS 1 原生入口；具体版本由设备系统、JetPack、驱动与包支持决定，不强制所有机器人安装同一 ROS 发行版。

官方 ROS 2 接口说明：[Topics, Services and Actions](https://docs.ros.org/en/jazzy/How-To-Guides/Topics-Services-Actions.html)。本轮 docs.ros.org 页面直接打开遇到防机器人页面；ROS bridge 与 SLAM 能力使用已读取的官方 GitHub 仓库核实，没有据此宣称通信实测通过。

## 两端 Agent 的实际协作示例

工作站提出“建立这层楼的地图并说明定位异常”；机器人端 Agent 根据自己的激光／相机能力、现有地图与资源选择已验证配置，启动本地建图任务。底层持续采样、定位和保存局部证据；机器人只在进展、关键异常或需要决策时回复。出现定位退化时，发送状态摘要和短数据片段，请工作站协助分析；得到建议后由端侧 Agent 判断适用性、执行授权范围内操作并验证。原始历史、硬件知识和当前设备状态保留在机器人本地，外部 Agent 建议不自动变成新的执行授权。

## 实施顺序和验证边界

先建立 ROS 2 基础适配与一条真实传感器观测闭环，再接入一个 SLAM 后端，形成启动、状态、产物、取消的完整能力；之后补 ROS 1 对等适配和第二种传感器，再扩充两端 Agent 的持久协作会话。模拟消息／录制数据先验证时钟、坐标、数据有效性与恢复语义，再按具体硬件验收。当前仅完成源码及资料核对，不宣称已具备全部能力。
