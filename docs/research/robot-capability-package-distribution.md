# 机器人能力包的网站分发与复现方案

日期：2026-09-07。问题：将本地调好的 Skills、工具与机器人控制流程显式发布到网站，让他人像拉取 Docker 镜像一样下载、部署和复现，是否可行？

状态：可行性与设计建议；本轮只核对源码和官方资料并归档，未实现下面的分发命令、部署下载站或上传任何用户包。

## 结论

可实现“选择能力包→拉取固定版本→绑定本机设备→检查环境→启动→实际验收”的流程。相同硬件与已支持的软件平台可接近一键复用；下载包本身不能让不同机器人自动兼容，也不能从作者设备的成功推定接收者设备通过验收。

本地用户内容默认私有、不得进入Loop ROS主项目push的规则继续有效。分享是单独流程：用户选择一个包，生成可审阅的发布副本，明确批准该版本后上传独立包仓库/下载目录。不能同步整个 ~/.loop；本次可行性询问不构成上传具体包的授权。

## 当前可复用基础（源码事实）

- [离线执行型Skills](../OFFLINE_SKILLS.md)、[offline_skill](../../toolchain/offline_skill.py)：SKILL.md、run.json、平台脚本、内容哈希、私有执行快照；通过已有process Node运行，不依赖聊天API。
- 现有save_profile只导出当前主机的启动/停止argv与cwd/env/remote声明；外部脚本、模型和依赖不会自动复制。不能直接把这个本机快捷方式宣称为跨机器可复现包。
- [进程工作流](../PROCESS_NODES.md)负责进程生命周期；[资源基础层](../RESOURCE_RUNTIME.md)负责共享准入。分发层不另造执行器或资源账本。
- [网站构建](../../scripts/build_website.py)目前只导出白名单静态资产；[网站说明](../../website/README.md)中的本地仿真服务不是公共包上传服务。尚无机器人包索引、拉取安装、版本切换或复现认证。

## 发布包内容（建议）

| 内容 | 用途 |
| --- | --- |
| package.json | 发布者、名称、版本、许可证、Loop最低版本、OS/CPU架构、硬件兼容范围、文件清单和校验值 |
| SKILL.md、run.json、scripts、必要工具源码 | 操作说明和实际启动/停止入口；普通文档Skill不自动成为可执行包 |
| requirements锁文件或容器镜像digest | 固定Python/系统/模型服务依赖；镜像按CPU架构区分 |
| 模型、URDF/MJCF、资源清单 | 小资产可随包；大模型/数据用有校验值的外部下载引用，并确认允许再分发 |
| device.example.json及参数schema | 设备角色、必填配置与兼容约束；不携带作者本机绑定值 |
| 环境检查、就绪检查、验收方案 | 区分依赖满足、进程存活、服务就绪、控制目标通过；检查本身的副作用应明确 |
| 验证记录 | 标明测试硬件、固件、平台、版本、日期、测试类型与结果，区分作者实测和接收者验收 |

设备地址、用户名/密钥、绝对路径、每台机器关节零位、相机外参、工作空间参数作为接收者本地配置。算法参数和设备级校准不能不加区分地复制。原包环境字段和脚本可能含本机信息，发布副本应做字段审查、参数化和文件预览；扫描不能替代人工确认。

## 作者与使用者流程（建议，尚未实现）

作者：从已验证流程选包→整理所需源码与资源→锁定依赖→参数化本机配置→在干净环境测试→预览发布清单→明确发布该版本。网站显示下载文件、兼容范围、依赖大小、许可证、审核/实测状态和校验信息。

接收者可有如下CLI体验，以下为拟议命令，不是当前可执行命令：

```text
loop pull publisher/robot-control@1.0.0
loop check publisher/robot-control@1.0.0 --device my-robot
loop run publisher/robot-control@1.0.0 --device my-robot
```

首次绑定设备并完成必要的校准/验收，以后在同一适配范围内复用。pull只下载和校验，不执行安装钩子或机器人动作；软件环境安装、服务启动和真机运动各自遵守既有权限。检查工具不能自动校准或使电机动作，除非具体步骤已获授权。

下载后使用版本目录和本地绑定文件分离存储，原子安装、避免覆盖运行中的版本，支持离线缓存。回滚只恢复软件/配置版本，不能撤销已发生的物理动作。

## 网站与存储选型

第一版建议：现有网站增加包目录与详情页，独立的HTTPS路径保存版本化归档及索引。发布端从明确的文件白名单构造副本；接收端核对可信索引中的大小、哈希和版本，解包限制越界、链接、数量及体积。单纯SHA256不证明发布者身份；发布来源由可信索引/HTTPS绑定，后续可增加签名验证与撤回标记。禁止覆盖已公开的同版本内容。

先支持维护者审核发布，不必首版开放匿名上传。后续多人投稿再加入身份、配额、审核、滥用处理和撤回机制。网站分发目录独立于Loop ROS主源码和用户私有状态，保留原项目发布白名单。

若未来需要兼容现成镜像仓库，可使用OCI artifact承载能力包/元数据，运行环境仍使用实际容器镜像。OCI官方说明支持非容器制品，并可关联签名等元数据：[OCI 1.1发布说明](https://opencontainers.org/posts/blog/2024-03-13-image-and-distribution-1-1/)。因此“像Docker一样分发”可复用既有存储机制，不必把全部控制逻辑或真机接口强制装进容器。

多进程启动应等待明确的就绪条件。Docker Compose也区分容器running与service_healthy，可作为依赖就绪设计参考：[Docker启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)。本项目仍通过Node管理已授权进程，不能仅凭子进程退出0就判定机器人就绪。

## 最小实施与验收顺序

1. 本地导出/检查/安装：归档与manifest、脱离本机路径、禁止覆盖、内容校验、用户绑定隔离；先用已审核network_discovery包验证传播链路。
2. 网站下载目录与pull：不可变版本、明确审核状态、兼容提示、失败不留下半安装目录；验证源机器导出、另一干净环境拉取。
3. 机器人复现：选一个明确型号及固件组合，以现有Host/推理/控制流程为样例，补齐环境锁定、设备绑定、就绪条件和实际目标验收。

第一阶段证明分发和安装，第二阶段证明跨环境获取，第三阶段才证明具体机器人控制复现。仅复制包、语法通过、容器运行或进程存活不能替代第三阶段验收。本轮没有进行这些跨机器实测。
