# Loop ROS 沙箱接入可行性

日期：2026-09-07。状态：可行性核对与设计建议，未实现或启用沙箱。

## 已核对事实

[OpenAI 官方沙箱说明](https://learn.chatgpt.com/docs/sandboxing)区分操作系统执行边界与审批策略，沙箱覆盖启动的命令及其文件／网络访问；平台分别提供原生实现。官方当前 Linux／WSL2 文档使用 bubblewrap，macOS 使用 Seatbelt，Windows 使用原生沙箱。这里核对的是产品机制，不表示其内部实现可以作为独立稳定库直接嵌入 Loop。

Loop 当前 `terminal/python_runner.py`、`toolchain/process_node.py` 以宿主用户权限执行；PermissionGate、脚本哈希、进程组和 ResourceManager 预算不构成操作系统隔离。plan／sim／real 是业务执行模式，不能充当沙箱强度。

## 建议实现

在共享运行基础层增加 SandboxPolicy／执行适配器，覆盖 Python、自编工具、离线 Skills、Agent 所派生命令和 Node 的程序启动。只把模型子进程关进沙箱不够：父进程 broker 执行的工具也必须经相应受限执行入口。

建议独立配置只读、工作区写入与显式宿主执行三类策略，并分别声明网络、可读／写目录、设备、GPU和凭据可见范围。工作区边界保护其他目录，不能防止授权工作区内的数据被删除；变更恢复仍依赖版本管理或快照。

第一阶段在 Linux 验证文件与网络隔离，复用平台机制，不自行模拟内核权限。普通代码任务在隔离环境运行；机械臂 Host、串口与 GPU 推理使用明确的设备／目录／网络访问配置。机器人实际动作继续走既有门禁和验收。GPU开放不意味着显存得到硬隔离；资源准入和隔离职责独立。

沙箱初始化失败应返回不可用，不能悄悄退回宿主全权限。只读诊断、停止与回收仍需可用；模型不能自行扩大沙箱策略。配置规则与平台能力均须报告真实状态。

## 验证边界

本轮只核对官方文档与当前代码；未安装 bubblewrap、启动容器、修改内核配置或改变当前会话权限。实施验收应至少覆盖工作区外读写、网络、子进程继承、broker执行路径、离线脚本、凭据与设备限制以及取消清理。Windows／macOS需要各自测试，不能据Linux结果宣称等价支持。
