# Loop ROS CLI：Python 性能与 C++ 迁移评估

日期：2026-09-07。问题：Python CLI 是否效率不足，未来是否需要整体迁移 C++。

结论：当前没有证据支持整体重写。保留 Python 的交互、模型编排、任务与记忆层；根据性能测量，将必要的 CPU 密集处理或高频设备控制放入 C++ 模块/独立节点。语言选择不替代延迟定位，C++ 本身不保证硬实时。

## 本地事实与推断

- terminal/interactive.py 使用 asyncio 与线程相关机制处理终端交互；terminal/llm.py 通过网络调用模型；terminal/setup.py 的启动连接检查包含网络请求，tests/test_fast_startup.py 覆盖普通/priority 探测和超时。这些是源码事实，不是性能基准。
- 当前经历的 API 格式错误、等待任务未出现在面板和记忆漏查是逻辑/接口行为，不能由重写 C++ 自动解决。
- 推断：端到端交互可能受网络/模型响应、启动探测、上下文规模、数据库访问和终端重绘影响。未运行 profiling，不能确认主要瓶颈或宣称具体提速比例。

## 建议路线

1. 分开测量进程启动至输入可用、按键至屏幕刷新、首 token 与完整回答、工具耗时、记忆查询以及 CPU/RSS，关注 p50/p95；区分正常链路与超时路径。
2. 若本地 UI/调度问题显著，先检查同步阻塞、重绘频率、重复查询与导入；若模型等待显著，优化请求数和上下文，而非更换 CLI 语言。
3. 只有 profiling 指向 Python 热点，或设备控制周期/抖动要求明确时，再局部 C++ 化。机器人高频控制与安全保护应独立于聊天工具循环，操作系统和通信路径也需验收。

假设示例：一次请求总计 5 秒，其中本地 Python 处理仅 50 毫秒，即使完全消除这部分，改善上限也只有 1%。这是解释瓶颈占比的算例，不是本项目测量。

## 原始来源

- Python 官方 threading 文档：https://docs.python.org/3.14/library/threading.html 。默认启用 GIL 的 CPython 线程不适合靠多线程加速纯 Python CPU 密集计算，但线程可用于 I/O 并发；也有多进程等路径。
- Python 官方 asyncio 文档：https://docs.python.org/3.13/library/asyncio.html 。异步 I/O 面向 I/O 密集及高层网络任务。
